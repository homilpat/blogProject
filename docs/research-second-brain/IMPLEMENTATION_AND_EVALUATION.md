# Knowledge Hub 2.0 — 구현 순서, 평가 및 승인 게이트

- 상태: 개발 계획, 코드 구현 전
- 원칙: 작은 단위 구현 → 테스트 → 사용자 리뷰/승인 → 다음 단계.
- `main`에 직접 구현하지 않고 기능 브랜치 사용. 이 문서 자체는 기획 단계다.

## 1. 단계별 로드맵

### Phase 0. 기준 상태 고정 및 안전성 개선 (P0)

작업:
- main 현재 동작을 테스트로 고정: 로그인, 노트 CRUD, 검색, 인용, 수정/삭제 후 재색인.
- 인증/권한 정비: 현재 `PostService`의 `authorId=1L` 고정 제거 및 게시글/노트 소유권 검증.
- `/api/rag/query` 비인증 공개 경로 해소. 개인 데이터가 노출되지 않게 모든 계층에 사용자 범위 적용.
- Qdrant 오류에 대한 인메모리 Fallback 및 임베딩 로딩 실패 시 가짜 벡터 Fallback 제거(연구/운영 모드).
- 현재 비동기 인덱싱의 상태/재시도 경로 설계.
- 기존 `categories` 필수 의존성의 단계적 제거 계획, 데이터 마이그레이션 초안.

합격: 기존 기능 회귀 없음, 다른 사용자 데이터 검색 불가능, DB/임베딩 실패가 성공으로 표시되지 않음.

### Phase 1. 지식 구조화와 증분 그래프 (P0)

작업:
- 출처, 개념, 주장, 관계, 원문 근거 위치 스키마 도입.
- 노트 저장 이벤트 기반 추출 작업 추가.
- 모델 구조화 추출 + 원문 일치 검사 + 중복 개념 후보 탐색.
- 증분 갱신, 데이터 버전/변경 이력, 삭제/수정 시 무효화.
- 그래프 탐색 API 및 소규모 관찰 UI.

합격: 노트 3개에서 동일 개념 재사용, 모호한 개념 오병합 방지, 노트 수정 시 stale 근거 제거.

### Phase 2. GraphRAG 복합 질의응답 (P0)

작업:
- 기존 Vector RAG를 기준선으로 유지.
- 내부 다중 질의/그래프 탐색/원문 재검색 전략 도입.
- 복수 청크/출처의 근거 수집과 Claim Judge 확장.
- 근거 부족과 충돌 정보 응답 정책 구현.

합격: 최소 2개 노트를 연결하는 평가 질문에서 근거 인용 정확도 및 답변 품질 개선을 확인. 품질 개선이 없다면 재설계.

### Phase 3. Autonomous Research Agent (P0)

작업:
- 하나의 Research Orchestrator, 내부 도구 호출 계약, 예산/실패/중단 상태.
- 관련 주장 탐색 → 가설 후보 → 비판 → 재탐색 → 지식 공백 → 연구 보고서.
- 생성 가설은 별도 저장, 검증된 사실/노트 원문에 자동 반영 금지.
- 연구 실행 기록과 보고서 조회 UI.

합격: 복수 노트 기반의 가설 1개 이상을 적절한 근거와 함께 제안하거나, 근거가 부족하면 가설 생성을 보류할 수 있어야 한다. 항상 가설을 생성할 필요는 없음.

### Phase 4. 학습 지원과 제품화 (P1)

작업:
- 노트 기반 문제 생성과 답안 피드백.
- 지식그래프 시각화, 관계 사용자 수정, 연구 보고서 비교/검색.
- 실행 성능, 자원 사용, 품질 모니터링 및 UX 개선.

합격: 문제의 사실 근거가 내부 노트에 존재하고, 사용자 평가와 객관적 사실 검증 상태가 혼동되지 않음.

## 2. 테스트 데이터셋 구축

데이터셋은 실제 사용자가 작성한 요약 노트 위주로, 충분한 권리와 권한을 가진 자료로 준비한다.

구성:
- 여러 노트의 공통 개념을 연결하는 복합 질문
- 단일 노트로 답할 수 있는 질문
- 일부 정보가 빠진 질문
- 전체 내부 코퍼스에 없는 정보에 대한 질문
- 서로 충돌하거나 조건이 다른 주장
- 같은 이름의 서로 다른 개념
- 노트 수정과 삭제에 따른 그래프 회귀
- 연구 가설 생성 및 실패 사례

초기 권장 평가 묶음(예시, 실제 목표치 아님):
- 단일 노트 질의 20개
- 다중 노트 질의 20개
- 근거 부족/모순 질의 20개
- 개념 동일성/관계 판단 30쌍
- 인간 검토가 가능한 연구 가설 사례 10개

**평가 데이터와 프롬프트 튜닝 데이터는 분리**하고, 개인 지식그래프에 정답을 직접 저장해 평가 데이터 누수를 일으키지 않는다.

## 3. 공정한 비교 실험

| 실험군 | 검색 | 추론 단계 |
| --- | --- | --- |
| A. 기존 Vector RAG | Qdrant 벡터 검색 | 동일한 응답/가설 생성 지시 |
| B. Hybrid GraphRAG | 벡터 + 그래프 | 동일한 모델 및 가능한 한 동일한 예산 |
| C. Research Agent | 벡터 + 그래프 + 적응적 재검색 | 가설 생성, 비판, 공백 분석 |

동일한 데이터, 질문, 원본 접근 범위, 모델을 사용한다. 토큰/지연/도구 호출 예산은 측정하고, 사용량 차이를 결과 해석에 포함한다. **연구 가설 생성 실험에서 A에도 같은 가설 생성 요청을 제공**해야 비교가 공정하다.

평가 지표:
1. Retrieval: context recall, relevant source recall, 문서/청크 근거 정확도.
2. Graph: 개념 병합 precision, 관계 precision/recall, provenance 유지율.
3. Answers: 인용 일치율, unsupported claim 비율, 내부 지식만으로 답하기 적절성, 근거 없는 질문에서 보류 정확도.
4. Research: 가설의 검증 가능성, 전제의 적합성, 반론의 실질성, 후속 실험 설계 가능성.
5. Gaps: 가설의 필수 전제 누락 탐지율, 제안 학습 주제의 타당성.
6. Runtime: p50/p95 지연, 모델 토큰, 도구 호출 수, 실패/재시도율.

가설 품질은 문장이 창의적이거나 길다는 이유만으로 고득점 처리하지 않는다. 최소 2인의 평가자가 독립적으로 근거/검증 가능성을 평가할 수 있도록 구체적 루브릭을 작성한다. 모델 평가자는 참고용이고 단독 정답 판정자가 아니다.

## 4. 세부 실패 검증

| 실패 유형 | 검증 |
| --- | --- |
| 존재하지 않는 근거 인용 | 모든 citation이 조회 가능한 노트 span에 대응해야 함 |
| 잘못된 개념 병합 | 동형이의어 사례 및 병합 취소 |
| 순환 강화 | AI 가설이 다음 실행에서 source fact로 승격되지 않음 |
| 근거 소실 | 노트 수정/삭제 시 관련 edge/hypothesis 상태 무효화 |
| 가짜 장애 복구 | Qdrant 및 임베딩 장애가 정상 응답처럼 취급되지 않음 |
| 사용자 정보 유출 | A/B 사용자 스코프 교차 검색 차단 |
| 무한 도구 호출 | 예산 초과 시 중단 상태 및 부분 결과 기록 |
| 가짜 독창성 | 외부 문헌 조사 없는 결과는 '개인 지식 기반 가설 후보'로만 표시 |
| 프롬프트 인젝션 | 노트 내부의 도구 실행/권한 변경 지시를 데이터로만 취급 |

## 5. 권장 구현 순서와 검토 게이트

각 Phase 종료 시 다음 결과물을 제출한다:
- 변경된 파일 목록과 설계 결정
- 구현 코드 Diff
- 자동화 테스트 실행 결과, 실패 시 재현 방법
- 추가된 DB 스키마/마이그레이션과 롤백 계획
- 전후 평가 결과 및 성능 영향
- 미해결 위험과 다음 단계 진입 제안

사용자 검토/승인 없이 다음 Phase의 구현을 시작하지 않는다.

## 6. 첫 번째 Proof of Concept

**입력:** 다음 세 종류의 사용자가 직접 쓴 요약 노트.
1. Pose Estimation 오류의 발생 및 한계
2. VLM의 시각적 추론 가능성과 제한
3. Active Learning의 불확실성 기반 선택 원리

**연구 요청:** "내가 공부한 세 기술을 조합해서 Pose Estimation 오류를 줄이는 검증 가능한 연구 가설을 찾아줘."

**기대 산출물:** 선택적 VLM 검토 같은 가설 후보(모델이 반드시 이 가설을 내야 하는 것은 아님), 연결 근거 2개 이상, 전제, 핵심 반론, 검증 실험, 추가 학습해야 할 지식 공백.

**반례 포함:** 일부 노트에서 관련 근거를 제거하거나 모순되는 근거를 추가할 때, 에이전트가 같은 결론을 무비판적으로 유지하지 않아야 한다.

## 7. 첫 번째 코드 작업 제안

바로 Agent 구현을 시작하지 않는다.

1. 기존 동작 검증 및 인증/사용자 범위 설계
2. source/concept/claim/relation/hypothesis와 provenance 계약 확정
3. 저장 이벤트에서 지식 추출/갱신의 데이터 플로우 설계
4. 3개 노트 PoC용 기준 데이터와 평가 질문 먼저 작성

위 항목을 완료한 뒤 Phase 1을 시작한다.
